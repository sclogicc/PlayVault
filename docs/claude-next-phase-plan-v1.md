# 当前目标

实现 `PlayVault` 的下一阶段核心能力：

**本地游戏自动发现 + 候选确认入库 + 自动计时主链路增强**

本阶段只做下面这条链路：

1. 用户配置一个游戏根目录
2. 系统扫描目录内可能的游戏 `exe`
3. 系统生成候选列表
4. 用户确认候选并加入游戏库
5. 系统基于已绑定 `exe` 自动生成 `session`
6. 系统能正确结束 `session`，并处理异常未结束记录

这不是整套系统的最终版，只是把“首次录入游戏”和“自动计时”这两条核心链路打通。

# 为什么做这个

当前项目已经有：

- 桌面应用骨架
- 本地数据库基础结构
- 游戏库基础 CRUD
- 页面骨架

但还缺少两个最关键的真实使用能力：

1. **首次使用成本仍然偏高**
   如果没有“本地游戏自动发现”，用户需要手动逐个录入游戏和 `exe`，这不符合项目的真实使用场景。

2. **自动计时能力还不够可靠**
   仅有简单的 `exe` 绑定还不够，需要补上：
   - 稳定启动判定
   - 稳定结束判定
   - 未完成 `session` 恢复
   - 异常结束标记

这一阶段完成后，`PlayVault` 才真正具备“能开始被持续使用”的基础。

# 涉及模块

本阶段只涉及以下模块：

- 游戏目录扫描模块
- 候选 `exe` 发现与确认模块
- 游戏库与 `GameExecutable` 绑定模块
- 进程轮询监听模块
- `Session` 生命周期管理模块
- 游戏发现页或游戏库中的“扫描导入”入口
- 基础设置中的扫描目录配置

不涉及：

- 截图监听
- 截图归类
- 总览统计完善
- 时间线完善
- 托盘增强
- 年度回顾

# 数据库变化

本阶段允许且建议进行以下数据库变更。

## 新增表

### `scan_roots`

用途：保存用户配置的游戏扫描根目录。

建议字段：

- `id`
- `path`
- `is_enabled`
- `last_scanned_at`
- `created_at`
- `updated_at`

### `discovered_executables`

用途：保存扫描发现的候选 `exe`，供用户确认。

建议字段：

- `id`
- `scan_root_id`
- `file_path`
- `file_name`
- `folder_name`
- `file_size`
- `modified_at`
- `score`
- `match_reasons`
- `status`
- `linked_game_id`
- `created_at`
- `updated_at`

`status` 只允许：

- `pending`
- `accepted`
- `rejected`
- `ignored`

## 现有表补字段

### `game_executables`

新增：

- `is_primary`

用途：

- 标记一个游戏的主记录 `exe`

### `sessions`

新增：

- `end_reason`
- `process_path`
- `created_at`
- `updated_at`

`end_reason` 只允许：

- `normal`
- `recovered`
- `manual`
- `unknown`

## 本阶段不要新增的表

不要新增：

- `unknown_processes`
- `game_scan_records`
- `activity_logs`
- 任何平台账号或成就相关表

# 后端/桌面层任务

## 1. 扫描根目录配置能力

实现：

- 新增扫描目录
- 删除扫描目录
- 启用/停用扫描目录
- 读取扫描目录列表

要求：

- 路径保存在本地数据库
- 允许多个根目录
- 不做自动联网或平台识别

## 2. 本地游戏目录扫描

实现：

- 对启用的扫描目录递归扫描子目录
- 扫描对象仅限 `.exe`
- 扫描深度限制为合理范围，建议 `3-5` 层
- 采集候选元信息：
  - 完整路径
  - 文件名
  - 所在文件夹名
  - 文件大小
  - 修改时间

要求：

- 不扫描 `.lnk`、`.bat`
- 不做复杂并发优化
- 不做全盘扫描

## 3. 候选 `exe` 规则评分

实现一个简单规则评分器，用于给发现的 `exe` 排序。

最低要求：

- 对明显非游戏程序降权：
  - `uninstall`
  - `setup`
  - `config`
  - `updater`
  - `patch`
  - `crash`
  - `launcher`
- 对更像游戏本体的候选加权：
  - 文件名与目录名相近
  - 文件体积明显不是小工具级别
  - 位于常见二进制目录时可少量加权

要求：

- 输出 `score`
- 输出 `match_reasons`
- 不做 AI 识别
- 不做图像识别
- 不做联网元数据抓取

## 4. 候选确认入库

实现：

- 用户可把候选 `exe` 加入游戏库
- 加入时自动创建：
  - `Game`
  - `GameExecutable`
- 默认游戏名优先取：
  1. 文件夹名
  2. `exe` 文件名去后缀

要求：

- 用户确认前不得自动加入游戏库
- 已加入的候选要更新状态为 `accepted`
- 被用户忽略的候选要更新状态为 `ignored`

## 5. 自动计时监听 v1

实现监听策略：

- 后台定时扫描进程列表
- 轮询间隔建议 `2 秒`

实现逻辑：

- 只对已绑定的 `exe` 生效
- 目标进程首次出现时，不要立刻建 `session`
- 目标进程连续存在一小段时间后再正式创建 `session`
- 目标进程消失时，进行二次确认，再结束 `session`

要求：

- 不使用复杂 Windows 事件监听
- 不做内核级或 WMI 复杂方案
- 不根据窗口前后台判断
- 不根据键鼠输入判断

## 6. 未完成 `session` 恢复

实现：

- 应用启动时检查数据库中 `ended_at` 为空的 `session`
- 自动补结束时间
- 写入 `end_reason = recovered`

要求：

- 不允许长期残留“未结束 session”
- 恢复逻辑必须稳定可重复执行

## 7. `session` 手动修正基础能力

本阶段后端至少提供数据接口支持：

- 删除错误 `session`
- 手动修改开始/结束时间
- 手动结束未完成 `session`

前端可以只做最小入口，但后端能力要有。

实现：

- 添加目录

- 启用/停用目录

必须支持：

## 3. 游戏库页增强

实现：

- 能继续编辑其显示名称、状态、备注、主 `exe`

如果本阶段时间有限，可以只保证：

- 游戏录入后可正常出现在库中

## 4. 游戏详情页最小增强

实现：

- 显示绑定的 `exe`

## 5. `session` 最小管理入口

实现最小可用 UI：

- 查看某个游戏的 `session` 列表
- 删除错误记录
- 手动结束未完成记录

如果时间有限，不做复杂弹窗编辑器，但至少保留基础操作入口。

# 验收标准

本阶段完成后，必须满足以下标准：

## 游戏发现链路

1. 用户可以在设置中配置一个游戏根目录
2. 系统可以扫描该目录中的候选 `exe`
3. 候选列表能展示基础信息、评分和原因
4. 用户可以把候选加入游戏库
5. 用户可以忽略候选
6. 候选确认后能生成对应的 `Game` 和 `GameExecutable`

## 自动计时链路

1. 对已绑定 `exe`，系统能自动生成 `session`
2. 短暂失败启动不会大量生成垃圾 `session`
3. 目标进程结束后，`session` 能被正确结束
4. 应用异常关闭后，未完成 `session` 能在下次启动时被恢复结束
5. `session` 至少能区分 `normal` 和 `recovered` 两类结束方式

## 稳定性

1. 类型检查通过
2. 不破坏当前已有游戏库 CRUD
3. 不破坏当前页面结构
4. 新增数据库迁移可正常执行
5. 同一候选 `exe` 不会被重复无限导入

# 不允许修改的部分

以下内容本阶段禁止修改：

1. **不要改产品定位**
- 不能把项目做成游戏平台启动器
- 不能把项目改成平台聚合器优先

2. **不要改自动计时口径**
- 不要加入“失焦暂停”
- 不要加入“无输入暂停”
- 不要加入“窗口最小化暂停”

3. **不要扩展到截图系统**
- 不做截图监听
- 不做截图归类
- 不做截图 UI 扩展

4. **不要引入复杂识别方案**
- 不做 AI 识别
- 不做图像识别
- 不做联网元数据抓取
- 不做 Steam/Epic/GOG 自动整合

5. **不要过度设计数据库**
- 不新增平台 ID 体系
- 不新增复杂日志系统
- 不新增成就系统
- 不新增社交/云同步字段

6. **不要一次做完整系统**
- 本阶段只解决：
  - 游戏目录扫描发现
  - 候选确认入库
  - 自动计时主链路增强

这阶段做完后，再进入下一轮。
