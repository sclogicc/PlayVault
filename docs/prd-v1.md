# PlayVault 产品需求文档 PRD v1

## 1. 文档定位

本文档是 PlayVault v1 的正式产品需求文档，用于指导后续原型设计、技术实现、测试验收与 AI 辅助开发。

文档目标：

- 把已经确认的需求转化为可执行的产品定义
- 明确 v1 的功能边界，避免范围不断膨胀
- 为其他 AI 或开发者提供统一、稳定、无歧义的理解基础

## 2. 产品定义

### 2.1 产品名称

`PlayVault`

### 2.2 产品一句话定义

一个面向 Windows 单机玩家的本地游戏游玩记录与截图归档系统。

### 2.3 产品定位

PlayVault 不是网页社区，也不是游戏平台启动器。  
它是一个以“本地、自动、长期整理”为核心价值的桌面型个人工具。

它解决的核心问题是：

- 用户想知道自己最近在玩什么、玩了多久
- 用户想留住每次游玩的时间轨迹，而不只是一个总数字
- 用户会积累大量截图，但缺少按游戏整理和回看的能力
- 用户希望系统尽量自动完成记录与归类，但接受少量人工确认

### 2.4 目标平台

- 首发平台：Windows
- 使用方式：单机本地使用
- 用户角色：单用户，无账号系统

## 3. 用户画像与核心场景

### 3.1 目标用户

目标用户具备以下特征：

- 以本地单机游戏为主要游戏方式
- 长期使用 PC 游玩
- 会使用 NVIDIA 截图功能保留游戏画面
- 有“记录、整理、回看”游戏经历的动机
- 不介意为系统配置少量初始信息，但希望日常尽量自动化

### 3.2 核心使用场景

1. 用户启动游戏，系统自动开始计时。
2. 用户退出游戏，系统自动结束本次游玩记录。
3. 用户在游玩时截图，系统自动监听到新图片并尝试归类。
4. 用户在空闲时打开 PlayVault，查看最近在玩的游戏、总时长和截图。
5. 用户把未识别截图手动归类到目标游戏。
6. 用户通过游戏详情页回看某个游戏的游玩历史与截图资产。

## 4. 产品目标与非目标

### 4.1 v1 产品目标

1. 稳定记录本地单机游戏游玩时长。
2. 用 `session` 维度保存每次游玩明细。
3. 提供游戏库，支持游戏状态、别名和截图文件夹名管理。
4. 支持 NVIDIA 截图目录监听与半自动归类。
5. 提供截图待整理区，支持人工确认和修正。
6. 提供总览、游戏详情、截图箱和时间线等核心页面。

### 4.2 v1 非目标

以下内容明确不纳入 v1：

- 自动识别通关状态
- Steam/Epic/GOG 平台深度同步
- 云同步与多设备共享
- 社交功能与社区内容
- 基于图像内容的 AI 游戏识别
- 复杂图片编辑器
- 手机版或 Web 云端版

## 5. 核心概念定义

### 5.1 Game

游戏实体，是系统中的主对象。  
一个游戏承载以下内容：

- 名称
- 显示名
- 别名
- 对应 `exe`
- 状态
- 标签
- 截图归档文件夹名
- 备注
- 相关 `session`
- 相关截图

### 5.2 Session

`session` 表示一次完整游玩记录。  
起点是目标游戏进程启动，终点是该进程退出。

一个 `session` 至少包含：

- 所属游戏
- 开始时间
- 结束时间
- 时长
- 识别来源

### 5.3 Screenshot

截图是用户通过 NVIDIA 截图功能产生的本地图片文件。  
截图在系统中会被索引、归类、展示和可选归档。

### 5.4 Backlog

积压库不是单独表，而是一种视图。  
它基于游戏状态、最后游玩时间和总时长生成。

### 5.5 Status

游戏状态是用户主动管理的字段，不由系统自动判断。  
v1 推荐状态：

- 未开始
- 游玩中
- 已通关
- 搁置
- 弃坑
- 已全成就

## 6. 产品原则

PlayVault v1 的设计与开发必须遵守以下原则：

1. 自动优先  
系统应尽量自动记录时长和归类截图，减少用户重复劳动。

2. 不确定不硬判  
无法准确归类时，进入待整理，而不是强行分配到某个游戏。

3. 安全优先  
默认只建立索引，不主动移动原始截图文件。

4. 明细优先  
必须存储 `session` 明细，不允许只保留汇总总时长。

5. 本地优先  
所有核心能力在本地离线可用，不依赖外部服务。

6. 长期可维护  
数据结构、页面结构和状态模型要为后续版本预留空间，但不提前过度开发。

## 7. 功能范围与优先级

### 7.1 P0 必做功能

#### 7.1.1 游戏库管理

功能点：

- 新增游戏
- 编辑游戏
- 停用游戏监控
- 配置别名
- 配置一个或多个 `exe`
- 配置截图归档文件夹名
- 配置标签与备注

验收标准：

- 用户可手动创建游戏条目
- 用户可为同一游戏绑定多个 `exe`
- 用户可更改显示名和文件夹名
- 已停用游戏不会再自动生成新 `session`

#### 7.1.2 自动计时

功能点：

- 监听本机进程
- 命中已绑定的游戏 `exe`
- 进程启动时创建进行中 `session`
- 进程退出时结束 `session`

验收标准：

- 游戏启动后可自动新增 `session`
- 游戏退出后该 `session` 可正确结束
- 时长计算正确
- 异常关闭后系统不会产生无限进行中的记录

#### 7.1.3 Session 管理

功能点：

- 查看全部 `session`
- 查看单游戏 `session`
- 手动删除 `session`
- 手动修正明显异常的记录

验收标准：

- 用户可以看到每条记录的开始时间、结束时间和时长
- 用户可以删除错误记录
- 用户修正后，统计结果能同步更新

#### 7.1.4 统计总览

功能点：

- 今日时长
- 本周时长
- 本月时长
- 每游戏总时长
- 最近在玩的游戏

验收标准：

- 用户能在总览页看到上述五类核心统计
- 统计结果基于 `session` 自动汇总
- 新 `session` 完成后，总览数据即时可见

#### 7.1.5 截图监听与归类

功能点：

- 配置 NVIDIA 截图来源目录
- 监听新增截图
- 记录截图时间和路径
- 基于 `session` 时间匹配游戏
- 自动归类成功时写入对应游戏
- 无法判断时进入待整理

验收标准：

- 新截图出现后系统能发现它
- 单候选场景下能自动归类
- 多候选或无候选场景下进入待整理
- 用户可以查看每张截图当前归类状态

#### 7.1.6 截图手动整理

功能点：

- 待整理截图列表
- 手动归类到指定游戏
- 标记忽略
- 打开原文件位置
- 可选复制/移动到归档目录

验收标准：

- 用户可以从待整理区把截图分配到目标游戏
- 用户可以忽略无效截图
- 用户可以打开图片实际所在目录
- 用户可以手动触发复制或移动

#### 7.1.7 游戏详情页

功能点：

- 查看游戏基本信息
- 查看总时长
- 查看全部 `session`
- 查看全部截图
- 查看最后游玩时间

验收标准：

- 每个游戏都有独立详情页
- 详情页信息完整、可回看
- 用户能从详情页直接进入截图浏览

### 7.2 P1 应做功能

#### 7.2.1 批量截图操作

- 批量归类
- 批量忽略
- 批量复制或移动

#### 7.2.2 数据安全

- 数据导出
- 数据备份
- 截图路径失效检测

#### 7.2.3 使用体验

- 托盘运行
- 开机自启动
- 基础搜索
- 基础筛选

### 7.3 P2 后续功能

- 历史截图批量导入辅助
- 路径级游戏识别增强
- 游戏封面管理增强
- 更丰富的年度统计
- 平台信息导入

## 8. 功能规则

### 8.1 自动计时规则

已确认规则如下：

- 游戏进程启动即开始计时
- 进程退出即结束计时
- 只要进程仍存活，就持续计时

规则说明：

- 不判断前台/后台
- 不判断是否有键鼠输入
- 不区分挂机与主动操作

该规则是用户明确选择的产品口径，v1 不得擅自改为“失焦暂停”或“无输入暂停”。

### 8.2 游戏识别规则

v1 主规则：

- 按 `exe` 文件名识别游戏

补充规则：

- 一个游戏可绑定多个 `exe`
- 一个 `exe` 在同一时间只能归属一个游戏
- 存在冲突时必须提醒用户修正

### 8.3 截图归类规则

新截图归类主逻辑：

1. 监听截图目录新增图片
2. 读取图片创建时间
3. 查找该时间点命中的进行中或最近结束的 `session`
4. 若仅命中一个候选游戏，则自动归类
5. 若存在多个候选，进入待整理
6. 若没有候选，进入待整理

补充说明：

- 不以文件名作为核心识别信号
- 不以图像内容识别为 v1 方案
- 待整理是正常状态，不算错误

### 8.4 截图存储规则

默认策略：

- 系统只建立索引，不自动搬运原始文件

用户可选操作：

- 复制到归档目录
- 移动到归档目录
- 保持原位

### 8.5 文件夹命名规则

每个游戏需要具备三个相关字段：

- 系统内部名称
- 用户显示名称
- 截图归档文件夹名

默认情况下，截图归档文件夹名等于显示名称，但允许用户修改。

### 8.6 忽略与异常规则

系统必须支持：

- 忽略指定进程
- 忽略指定截图
- 清理无效记录
- 标记异常 `session`

1. 总览 Dashboard

## 12. 用户故事

1. 作为单机玩家，我希望启动游戏后自动开始计时，这样我不用手动点开始。
2. 作为单机玩家，我希望退出游戏后自动结束计时，这样每次游玩都能自然形成记录。
3. 作为截图很多的玩家，我希望系统自动发现 NVIDIA 新截图并尝试归类，这样我不用每次都自己找图。
4. 作为整理控，我希望给每个游戏配置自定义截图文件夹名，这样磁盘结构能符合我的习惯。
5. 作为长期玩家，我希望看到某个游戏的全部 `session` 和截图，这样我能回顾自己玩它的轨迹。
6. 作为想清 backlog 的玩家，我希望按状态和最后游玩时间筛选游戏，这样我知道哪些游戏被我搁置了。

## 13. 边界场景与异常场景

### 13.1 边界场景

- 同一个游戏绑定多个 `exe`
- 同时开启多个被监控游戏
- 游戏异常崩溃或强制结束
- 启动器和游戏本体先后启动
- 截图时间落在游戏切换临界点

### 13.2 系统要求

对于所有边界场景，系统必须满足：

- 不崩溃
- 不生成不可恢复的脏数据
- 可通过人工修正恢复到正确状态

## 14. 验收标准

### 14.1 功能验收

以下标准全部满足后，才能认为 v1 达到交付标准：

1. 已配置游戏可自动生成 `session`
2. 每条 `session` 的开始、结束、时长准确可见
3. 总览页统计结果与 `session` 汇总一致
4. NVIDIA 新截图可被系统发现
5. 单候选截图能自动归类
6. 不确定截图进入待整理区
7. 用户可以手动归类或忽略截图
8. 游戏详情页能同时展示时长与截图

### 14.2 产品验收

从用户感知角度，v1 必须达到以下标准：

- 用户不需要每天手动记时
- 用户能感到截图整理负担明显降低
- 用户能通过总览和详情页形成“我最近玩了什么”的清晰认知
- 用户能信任系统不会乱动原始截图文件

## 16. 冻结决策

以下事项已确认，后续设计与开发不得偏离：

1. 截图归档目录结构采用“按游戏”，v1 不增加“年月”子目录。
2. 历史截图不进入 v1 主链路，v1 只处理新截图监听与新截图归类。
3. 游戏封面不作为 v1 核心功能，v1 不做自动抓取。
4. 数据导出以完整数据库备份优先，CSV 导出可后续补充。
5. 游戏状态固定为：未开始、游玩中、已通关、搁置、弃坑、已全成就。
6. 截图来源目录采用全局配置，不为单个游戏单独配置来源目录。
7. 自动归类仅匹配截图产生时刻处于进行中的 `session`，v1 不增加前后时间容差。
8. 多候选命中时一律进入待整理，系统不得自动猜测归属。
9. 默认只建立截图索引；用户手动归档时，默认推荐复制，不默认移动。
10. `托盘运行` 进入 v1；`开机自启动` 进入 P1，不属于 v1 必做项。
