# PlayVault 自动档案卡设计规范

## 1. 设计目的

自动档案卡用于在游戏被清理后，保留一张可长期回顾的“经历封面”。它不是表单，也不是结算弹窗；所有核心信息由系统从既有 Game、Session 与 Screenshot 数据自动生成。

用户进入游戏详情页时，普通游戏展示“正在游玩”的详情头图；当用户点击“封存此游戏”后，同一详情页切换为“历史档案”模式。页面不打断用户，也不要求任何填写。

## 2. 信息层级

### 第一层：一眼识别这段经历

页面顶部为沉浸式头图，使用已保存的背景图和封面。标题旁显示低干扰的“已封存”状态，不展示安装路径、启动按钮或管理操作。顶部只呈现四个自动统计：累计游玩时长、Session 数量、首次游玩日期、最后游玩日期。

### 第二层：看到经历如何发生

头图下方是一条三点时间轴：首次启动、最后一次 Session、封存日期。若未来增加通关确认或精选截图等事件，可在这条时间轴上以额外节点显示；不需要新增独立页面。

### 第三层：留下可见的画面

页面展示 0–3 张“封存截图”。这些截图不是默认复制所有原图，而是用户在封存动作时可选择保留的画面。被复制到 PlayVault 档案目录的截图带有星标；外部文件仍保留路径索引，但不作为长期可靠资产承诺。

## 3. 触发与交互

| 时机 | 系统行为 | 用户是否需要输入 |
|---|---|---|
| 游戏结束 | 自动写入 Session 时长、结束时间和关联截图；不弹出总结窗口 | 否 |
| 用户点击“封存此游戏” | 展示一个极简确认弹窗，说明游戏文件可以随后由用户自行清理 | 一次确认 |
| 封存确认弹窗 | 默认选项为“只保留档案记录”；可额外勾选最多 3 张截图复制到档案目录 | 可跳过 |
| 封存完成 | 游戏变为 `archived`，自动生成档案头图、统计卡和时间轴 | 否 |
| 后续回顾 | 从“历史档案”入口进入，只读浏览；可恢复为普通档案，但不自动恢复游戏文件 | 否 |

## 4. 不出现的内容

自动档案卡不包含长篇总结输入、心情问卷、评分强制项、成就同步、社区动态、商店卡片或推荐流。若未来用户确实需要主观记忆，只提供可选的 30 字短句或几个感受标签；它不影响档案卡生成。

## 5. 推荐数据模型

第一版无需单独复制所有 Session。可在 `games` 表中新增：

| 字段 | 类型 | 说明 |
|---|---|---|
| `archive_status` | `active` / `archived` | 是否进入历史档案模式 |
| `archived_at` | 可空日期 | 用户确认封存的时间 |
| `archive_screenshot_ids` | JSON 数组 | 最多 3 个精选截图的 ID |
| `archive_cover_path` | 文本，可复用原封面 | 封存时使用的封面快照路径 |
| `archive_background_path` | 文本，可复用原背景 | 封存时使用的背景快照路径 |

截图表新增可选字段：

| 字段 | 类型 | 说明 |
|---|---|---|
| `is_archived_highlight` | 布尔值 | 是否为封存精选截图 |
| `preserved_path` | 可空文本 | 可选复制到 PlayVault 档案目录后的稳定路径 |

## 6. 第一版验收标准

1. 用户封存游戏后，删除本地游戏文件不会删除游戏、Session 和截图索引。
2. 已封存游戏的详情页不再显示“启动游戏”，只显示经历回顾内容。
3. 页面能自动显示四项统计与首次/最后游玩节点，不要求用户填写。
4. 用户可选择不保存截图，也可最多复制 3 张截图到档案目录。
5. 复制后的精选截图即使原截图被用户清理，也能在档案页中正常浏览。
6. 已封存游戏可在单独的“历史档案”入口中被检索和打开。
