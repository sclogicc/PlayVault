# PlayVault 需求草案 v1

## 1. 文档目标

本文档用于明确 PlayVault 第一阶段产品范围、核心规则与后续迭代边界，避免在设计和开发阶段因产品定义不清而反复返工。

当前版本基于以下前提：

- 使用平台为 Windows
- 使用对象为单用户、本地使用
- 核心场景为本地单机游戏游玩记录
- 截图来源以 NVIDIA 截图功能为主
- 第一阶段优先实现自动记录与半自动归类，不追求全自动零误判

## 2. 产品定位

PlayVault 是一个面向单机玩家的本地游戏游玩记录与截图归档系统。

它不是单纯的计时器，也不是单纯的图片查看器，而是把以下几件事情统一起来：

- 自动记录每个游戏的游玩时长
- 保存每次游玩的明细记录
- 管理游戏库与游戏状态
- 半自动整理和归类游戏截图
- 帮助用户回看自己的游玩轨迹与积压情况

## 3. 目标用户

目标用户画像：

- 主要游玩本地单机游戏的 PC 玩家
- 有长期记录游玩时长的需求
- 会使用 NVIDIA 截图功能保留大量游戏截图
- 希望把截图和游戏记录统一管理
- 接受少量人工确认，但希望系统尽可能自动完成归类

## 4. 产品目标

第一阶段产品目标如下：

1. 自动记录用户本地单机游戏的游玩时长
2. 为每次游玩生成一条可追溯的 `session` 记录
3. 建立本地游戏库，支持游戏状态与别名管理
4. 监听 NVIDIA 截图目录，并尽可能自动将截图归类到对应游戏
5. 为用户提供截图待整理区和手动修正能力
6. 通过总览、游戏详情和时间线，让用户清楚知道自己最近在玩什么、玩了多久、积压了哪些游戏

## 5. 核心概念

### 5.1 游戏

系统中的“游戏”是一个独立实体，用于承载以下信息：

- 游戏名称
- 显示名称
- 别名
- 识别用的 `exe` 文件名
- 可选的安装路径或路径特征
- 截图归档文件夹名称
- 标签与平台信息
- 游戏状态

### 5.2 Session

`session` 表示一次完整的游玩记录。

示例：

- 游戏：Cyberpunk 2077
- 开始时间：2026-07-08 20:14
- 结束时间：2026-07-08 23:02
- 时长：2 小时 48 分钟

系统必须保存每一条 `session`，而不是只保存累计总时长。  
原因是总时长可以由 `session` 汇总得到，但如果只保存总时长，将无法支撑：

- 日/周/月统计
- 最近在玩什么
- 时间线回顾
- 截图与游玩记录的时间关联

### 5.3 总时长

总时长是基于 `session` 聚合出的统计结果，用于表示某个游戏的累计游玩时间。

### 5.4 截图

截图是用户在游玩过程中通过 NVIDIA 截图功能保存的图片文件。

在系统中，截图需要支持以下状态：

- 已归类：已经归属到某个游戏
- 待整理：系统无法确定归属，等待用户确认
- 已忽略：用户明确标记为不需要管理的图片

### 5.5 游戏状态

第一阶段建议支持以下状态：

- 未开始
- 游玩中
- 已通关
- 搁置
- 弃坑
- 已全成就

### 5.6 积压库

积压库不是单独的数据实体，而是基于游戏状态与游玩记录生成的视图。

典型维度包括：

- 已入库但未开始
- 已开始但未通关
- 长时间未游玩
- 已通关待整理

## 6. 核心规则

### 6.1 自动计时规则

根据当前确认的需求，第一阶段采用以下规则：

- 当目标游戏进程启动时，立即开始计时
- 只要目标进程仍然存活，就持续计时
- 当目标游戏进程退出时，立即结束计时
- 每次开始到结束形成一条 `session`

该规则优点：

- 逻辑简单明确
- 第一阶段实现难度低
- 用户容易理解和预期系统行为

该规则局限：

- 如果游戏挂后台但进程未退出，仍然会继续计时
- 如果启动器与游戏本体混淆，可能产生误记录

### 6.2 游戏识别规则

第一阶段以 `exe` 文件名作为主识别键。

为降低误判风险，系统仍应预留以下辅助能力：

- 用户可手动绑定该 `exe` 对应哪个游戏
- 允许同一游戏配置多个 `exe`
- 后续版本可增加路径辅助识别

### 6.3 忽略规则

系统应支持忽略某些不应被识别为游戏的进程，例如：

- 启动器
- 配置工具
- Mod 工具
- 存档管理器

### 6.4 截图归类规则

第一阶段截图归类采用“自动识别优先，人工确认兜底”的策略。

自动归类优先使用以下信号：

1. 截图生成时间
2. 截图生成时刻正在进行的游戏 `session`
3. 用户维护的 `exe -> 游戏` 绑定关系
4. 用户配置的截图来源目录

推荐归类逻辑：

- 系统监听 NVIDIA 截图目录中的新增图片
- 记录新增截图的生成时间
- 查找该时间点处于进行状态的游戏 `session`
- 如果只有一个匹配游戏，则自动归类
- 如果存在多个候选或无法判断，则进入“待整理”

### 6.5 截图文件管理规则

第一阶段默认采用“索引优先”的安全策略。

默认行为：

- 系统记录截图路径与归属关系
- 系统不主动移动原始截图文件

用户可选行为：

- 手动复制到统一归档目录
- 手动移动到统一归档目录
- 保持原位，仅建立索引

这样设计的原因：

- 降低误判造成的文件整理风险
- 保留 NVIDIA 原始截图目录
- 方便后续修正归类结果

### 6.6 截图文件夹规则

每个游戏都应支持以下字段：

- 显示名称
- 系统内部名称
- 截图归档文件夹名

默认情况下，截图归档文件夹名等于游戏名称。  
用户可以将文件夹名改为自定义别名，例如：

- `Elden Ring`
- `艾尔登法环`
- `老头环`

## 7. 第一阶段功能范围

### 7.1 必须实现

1. 游戏库管理
- 新增、编辑、停用游戏
- 配置游戏名称、别名、`exe` 文件名、状态、标签、截图文件夹名

2. 自动计时
- 监听目标游戏进程
- 自动开始/结束计时
- 自动生成 `session`

3. Session 管理
- 查看每个游戏的游玩记录
- 查看每条 `session` 的开始、结束和时长
- 支持手动删除或修正异常记录

4. 统计总览
- 今日时长
- 本周时长
- 本月时长
- 每个游戏总时长
- 最近在玩的游戏

5. 截图管理
- 配置 NVIDIA 截图来源目录
- 扫描新增截图
- 自动归类能识别的截图
- 未识别截图进入待整理区
- 支持手动将截图归类到某个游戏

6. 游戏详情页
- 查看游戏基本信息
- 查看总时长
- 查看该游戏全部 `session`
- 查看该游戏全部截图

### 7.2 应该实现

1. 批量操作
- 批量归类截图
- 批量忽略截图

2. 数据安全
- 本地数据库备份与导出
- 截图路径校验

3. 体验能力
- 托盘运行
- 开机自启动
- 基础搜索与筛选

### 7.3 暂不实现

- 自动识别通关状态
- 自动同步 Steam/Epic/GOG 成就
- 云同步
- 多设备共享
- 社交功能
- 基于图片内容的 AI 识别游戏
- 复杂的截图编辑能力

## 8. 页面结构建议

### 8.1 总览页

展示内容：

- 今日/本周/本月游玩时长
- 最近在玩的游戏
- 最近新增截图
- 待整理截图数量
- 按日期查看的游玩热力图或时间统计

### 8.2 游戏库

展示内容：

- 游戏名称
- 状态
- 总时长
- 最后游玩时间
- 截图数量

支持筛选：

- 全部
- 游玩中
- 已通关
- 积压
- 搁置

### 8.3 游戏详情页

展示内容：

- 游戏封面或占位图
- 基本信息与状态
- 总时长
- 最近游玩记录
- 全部 `session`
- 全部截图

### 8.4 截图箱

展示内容：

- 已归类截图
- 待整理截图
- 已忽略截图

关键能力：

- 按时间排序
- 批量归类
- 打开原文件位置
- 复制/移动到归档目录

### 8.5 时间线

展示内容：

- 按日期查看游玩记录
- 每日包含多个 `session`
- 支持查看某次游玩期间产生的截图

### 8.6 设置页

配置项：

- NVIDIA 截图目录
- 统一截图归档目录
- 自动扫描开关
- 开机启动
- 托盘行为
- 备份与导出

## 10. 关键场景

### 10.1 自动记录游玩

1. 用户启动某个已配置游戏
2. 系统识别到目标 `exe`
3. 系统创建新的进行中 `session`
4. 用户退出游戏
5. 系统结束该 `session` 并写入时长

### 10.2 自动归类新截图

1. 用户在游戏中使用 NVIDIA 截图
2. 系统监听到截图目录新增文件
3. 系统读取文件创建时间
4. 系统匹配该时间点所在的 `session`
5. 若唯一匹配，则自动归类到对应游戏
6. 若无法唯一匹配，则放入待整理

### 10.3 手动整理待归类截图

1. 用户进入截图箱
2. 查看待整理截图
3. 手动选择截图归属的游戏
4. 系统更新索引
5. 用户可选复制或移动到归档目录

## 11. 风险与边界

第一阶段已知风险：

- 某些游戏存在多个进程，主进程不稳定
- 启动器可能被误识别为游戏
- 游戏后台挂起时仍会持续计时
- 截图发生在游戏切换边界时，归类可能不准确
- 历史截图缺乏当时游玩上下文，自动识别能力有限

对应策略：

- 提供忽略名单
- 提供手动修正能力
- 对不确定截图使用待整理机制
- 采用索引优先而非强制移动原图

## 12. 第一阶段成功标准

若满足以下条件，可视为 v1 成功：

1. 用户能稳定记录本地单机游戏时长
2. 用户能查看每个游戏的累计时长和游玩明细
3. 用户能通过系统知道最近在玩什么
4. 大部分新截图可以被自动归类或快速手动整理
5. 用户能通过游戏详情页同时看到时长记录与截图资产

## 14. 已确认结论

以下事项已在 v1 范围内确认：

1. 截图归档目录结构采用“按游戏”，不增加“年月”子目录。
2. 第一阶段不将历史截图导入纳入主链路，仅处理新截图监听与归类。
3. 第一阶段不将封面图管理作为核心功能。
4. 游戏状态采用 6 种固定枚举：未开始、游玩中、已通关、搁置、弃坑、已全成就。
5. 数据导出优先提供完整数据库备份，CSV 可后续补充。
6. 截图来源目录采用全局配置，不为单个游戏单独配置来源目录。
7. 自动归类仅匹配进行中的 `session`，不增加时间容差。
8. 多候选游戏同时命中时，一律进入待整理。
9. 截图文件默认只建立索引，手动归档时默认推荐复制。
10. `托盘运行` 属于 v1 范围，`开机自启动` 属于 P1 范围。
